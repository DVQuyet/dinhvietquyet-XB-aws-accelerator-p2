# W9-D1 — GitOps & CI/CD

## 1. Mục tiêu học ngày D1

Ngày W9-D1 tập trung vào GitOps và CI/CD.

Mục tiêu chính của ngày học là hiểu cách chuyển từ cách deploy thủ công bằng `kubectl apply` sang cách deploy theo GitOps.

Ở W8, em đã làm quen với Kubernetes/minikube và có thể deploy manifest bằng tay. Sang W9, mục tiêu là không còn apply manifest thủ công nữa. Thay vào đó, toàn bộ cấu hình Kubernetes được lưu trong Git. Khi Git thay đổi, ArgoCD sẽ tự phát hiện và đồng bộ trạng thái trong Git vào Kubernetes cluster.

Luồng tổng quát:

```txt
Developer sửa manifest
        ↓
Tạo Pull Request
        ↓
GitHub Actions chạy kiểm tra / plan
        ↓
Review và merge vào main
        ↓
ArgoCD phát hiện Git thay đổi
        ↓
ArgoCD sync vào Kubernetes cluster
        ↓
Ứng dụng được deploy theo trạng thái trong Git
```

Cách hiểu ngắn gọn:

```txt
GitHub = nơi lưu bản thiết kế
GitHub Actions = người kiểm tra bản thiết kế
ArgoCD = người tự triển khai bản thiết kế vào Kubernetes
Kubernetes = nơi app chạy thật
```

## 2. GitOps là gì?

GitOps là cách quản lý hệ thống bằng Git.

Trong GitOps, Git được xem là nguồn sự thật, tức là trạng thái mong muốn của hệ thống phải nằm trong Git. Nếu cluster thật khác với Git, công cụ GitOps như ArgoCD sẽ phát hiện và đưa cluster về đúng trạng thái được khai báo trong Git.

Ví dụ:

Trong Git có file Deployment ghi:

```yaml
replicas: 3
image: nginx:1.27
```

Nghĩa là trạng thái mong muốn là:

```txt
Ứng dụng chạy 3 bản
Dùng image nginx:1.27
```

Nếu ai đó vào cluster sửa tay còn 1 replica:

```bash
kubectl scale deployment web --replicas=1
```

thì cluster thật đang bị lệch so với Git. GitOps gọi tình trạng này là drift. ArgoCD sẽ phát hiện cluster đang khác Git và sync lại về 3 replicas.

---

## 3. Bốn nguyên tắc GitOps

### 3.1. Declarative

Declarative nghĩa là khai báo trạng thái mong muốn, không cần mô tả từng bước thực hiện.

Ví dụ Kubernetes manifest:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
```

File này không nói:

```txt
Bước 1: tạo pod thứ nhất
Bước 2: tạo pod thứ hai
Bước 3: tạo pod thứ ba
```

Nó chỉ nói:

```txt
Tôi muốn có 3 replicas.
```

Kubernetes và ArgoCD sẽ tự xử lý để đạt trạng thái đó.

Kết luận:

```txt
Declarative = nói muốn kết quả cuối cùng là gì.
```

---

### 3.2. Versioned and Immutable

Versioned and Immutable nghĩa là trạng thái mong muốn phải được lưu có lịch sử thay đổi.

Vì manifest nằm trong Git nên mỗi thay đổi đều có commit.

Ví dụ:

```txt
Commit A: image = web:v1
Commit B: image = web:v2
Commit C: replicas = 3
```

Lợi ích:

* Biết ai sửa gì.
* Biết lúc nào sửa.
* Có thể review trước khi merge.
* Có thể rollback bằng cách quay lại commit cũ.
* Mentor có thể nhìn repo để đánh giá evidence.

Kết luận:

```txt
Git giúp hạ tầng có lịch sử rõ ràng, không còn kiểu sửa tay rồi quên.
```

---

### 3.3. Pulled Automatically

Pulled Automatically nghĩa là agent trong cluster tự kéo cấu hình từ Git về.

Trong GitOps chuẩn, luồng deploy thường là pull-based:

```txt
ArgoCD nằm trong cluster
ArgoCD quan sát Git repository
Khi Git thay đổi, ArgoCD tự pull manifest về
ArgoCD sync manifest vào Kubernetes
```

So sánh với cách cũ:

```txt
Cách cũ:
Laptop của em → kubectl apply → Kubernetes cluster

GitOps:
Git repository → ArgoCD tự pull → Kubernetes cluster
```

Điểm quan trọng:

```txt
Không cần máy cá nhân của em giữ quyền apply trực tiếp vào cluster.
ArgoCD là thành phần chịu trách nhiệm đồng bộ.
```

---

### 3.4. Continuously Reconciled

Continuously Reconciled nghĩa là hệ thống liên tục so sánh trạng thái thật với trạng thái mong muốn.

Có 2 trạng thái:

```txt
Desired state = trạng thái mong muốn trong Git
Actual state = trạng thái thật trong Kubernetes cluster
```

Nếu 2 trạng thái giống nhau:

```txt
Application = Synced
```

Nếu 2 trạng thái khác nhau:

```txt
Application = OutOfSync
```

Ví dụ:

Git ghi:

```yaml
replicas: 3
```

Cluster thật đang là:

```txt
replicas: 1
```

ArgoCD sẽ thấy lệch và sync lại:

```txt
replicas: 3
```

Kết luận:

```txt
Reconciliation = quá trình kéo actual state về giống desired state.
```

## 4. Các khái niệm quan trọng trong GitOps

### 4.1. Desired State

Desired State là trạng thái mong muốn của hệ thống.

Ví dụ desired state có thể gồm:

```txt
Deployment chạy image nào
Service mở port nào
ConfigMap chứa cấu hình nào
Ingress route domain nào
Namespace nào cần tồn tại
```

Trong GitOps, desired state nên được lưu trong Git.

---

### 4.2. Actual State

Actual State là trạng thái thật đang tồn tại trong cluster.

Ví dụ:

```bash
kubectl get deployment
kubectl get pod
kubectl get svc
```

Các lệnh này cho biết cluster thật đang có gì.

---

### 4.3. Drift

Drift là khi actual state bị lệch khỏi desired state.

Ví dụ Git muốn:

```txt
image = web:v1
replicas = 3
```

Nhưng cluster thật là:

```txt
image = web:v2
replicas = 1
```

Đây là drift.

Nguyên nhân drift có thể là:

* Có người sửa tay bằng `kubectl`.
* Có script apply trực tiếp vào cluster.
* Có người sửa resource trong UI.
* Có lỗi trong quá trình deploy.

---

### 4.4. Reconciliation

Reconciliation là quá trình làm cho actual state giống lại desired state.

Trong GitOps:

```txt
ArgoCD quan sát Git
ArgoCD quan sát Kubernetes
Nếu khác nhau thì báo OutOfSync
Khi sync, ArgoCD apply manifest để cluster giống Git
```

## 5. GitHub Actions là gì?

GitHub Actions là nền tảng CI/CD của GitHub.

Nó giúp tự động chạy các bước như:

```txt
Build
Test
Validate YAML
Check Kubernetes manifest
Run plan
Deploy sau khi merge
```

Trong W9-D1, GitHub Actions dùng cho 2 việc chính:

```txt
1. plan-on-PR
2. apply-on-merge
```

---

## 6. Các thành phần chính của GitHub Actions

### 6.1. Workflow

Workflow là file YAML định nghĩa pipeline tự động.

Workflow nằm trong thư mục:

```txt
.github/workflows/
```

Ví dụ:

```txt
.github/workflows/plan-on-pr.yaml
.github/workflows/apply-on-merge.yaml
```

Một repository có thể có nhiều workflow.

---

### 6.2. Event

Event là sự kiện kích hoạt workflow.

Ví dụ:

```yaml
on:
  pull_request:
```

Nghĩa là workflow chạy khi có Pull Request.

Ví dụ khác:

```yaml
on:
  push:
    branches:
      - main
```

Nghĩa là workflow chạy khi có push vào branch `main`.

Trong ngày D1, 2 event quan trọng nhất là:

```txt
pull_request = dùng để kiểm tra trước khi merge
push main = dùng để triển khai sau khi merge
```

---

### 6.3. Job

Job là một nhóm công việc trong workflow.

Ví dụ:

```yaml
jobs:
  validate:
    runs-on: ubuntu-latest
```

Ở đây có job tên là `validate`.

Một workflow có thể có nhiều job:

```txt
validate
test
build
deploy
```

---

### 6.4. Step

Step là từng bước nhỏ trong job.

Ví dụ:

```yaml
steps:
  - uses: actions/checkout@v4
  - run: kubectl version --client
  - run: kubectl apply --dry-run=client -f k8s/
```

Giải thích:

```txt
Step 1: lấy source code từ repo
Step 2: kiểm tra kubectl
Step 3: validate manifest Kubernetes
```

---

### 6.5. Runner

Runner là máy chạy workflow.

Ví dụ:

```yaml
runs-on: ubuntu-latest
```

Nghĩa là GitHub cấp một máy Ubuntu tạm thời để chạy workflow.

---

### 6.6. Action

Action là block có sẵn để tái sử dụng.

Ví dụ:

```yaml
- uses: actions/checkout@v4
```

Action này dùng để checkout source code từ GitHub repository vào runner.

---

## 7. Plan-on-PR là gì?

Plan-on-PR nghĩa là khi mở Pull Request, hệ thống chỉ kiểm tra trước chứ chưa deploy thật.

Mục tiêu:

```txt
Phát hiện lỗi trước khi merge
Tránh phá cluster thật
Cho mentor/team review trước
```

Ví dụ workflow:

```yaml
name: plan-on-pr

on:
  pull_request:
    branches:
      - main

jobs:
  validate:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout source code
        uses: actions/checkout@v4

      - name: Check Kubernetes manifest syntax
        run: |
          kubectl apply --dry-run=client -f cloud/w9/day-a/k8s/
```

Giải thích:

```txt
Khi có PR vào main
GitHub Actions tạo runner Ubuntu
Checkout source code
Chạy kubectl dry-run để kiểm tra manifest
Nếu manifest lỗi thì workflow fail
Nếu workflow fail thì không nên merge
```

Ghi nhớ:

```txt
PR = kiểm tra trước
Không deploy thật trên PR
```

---

## 8. Apply-on-merge là gì?

Apply-on-merge nghĩa là khi Pull Request đã được merge vào `main`, hệ thống mới triển khai.

Ví dụ workflow:

```yaml
name: apply-on-merge

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout source code
        uses: actions/checkout@v4

      - name: Deployment note
        run: |
          echo "Manifest merged to main. ArgoCD will detect and sync."
```

Trong GitOps chuẩn, GitHub Actions không nhất thiết phải chạy `kubectl apply` trực tiếp vào cluster. Lý do là ArgoCD sẽ tự quan sát Git và tự sync.

Luồng đúng hơn:

```txt
Merge vào main
      ↓
Manifest trong Git thay đổi
      ↓
ArgoCD phát hiện OutOfSync
      ↓
ArgoCD sync vào cluster
```

Ghi nhớ:

```txt
Merge = xác nhận desired state mới
ArgoCD = người triển khai desired state mới
```

## 9. ArgoCD là gì?

ArgoCD là công cụ GitOps cho Kubernetes.

Nhiệm vụ của ArgoCD:

```txt
Theo dõi manifest trong Git
So sánh Git với Kubernetes cluster
Báo trạng thái Synced hoặc OutOfSync
Sync manifest từ Git vào cluster
Hiển thị health của app
```

Luồng hoạt động:

```txt
Git Repository
      ↓
ArgoCD Application
      ↓
Kubernetes Cluster
```

Một ArgoCD Application thường cần biết:

```txt
repoURL = repo Git chứa manifest
path = thư mục chứa manifest trong repo
targetRevision = branch/commit/tag cần dùng
destination.server = cluster đích
destination.namespace = namespace đích
```

Ví dụ Application manifest:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: demo-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/<your-user>/<your-repo>
    targetRevision: main
    path: cloud/w9/day-a/k8s
  destination:
    server: https://kubernetes.default.svc
    namespace: demo
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

Giải thích:

```txt
metadata.name = tên app trong ArgoCD
repoURL = repo chứa manifest
targetRevision = branch main
path = thư mục chứa YAML Kubernetes
destination.server = cluster hiện tại
destination.namespace = namespace deploy
automated.prune = xóa resource không còn trong Git
automated.selfHeal = tự sửa nếu cluster bị drift
```

## 10. ArgoCD vs Flux

ArgoCD và Flux đều là GitOps tool cho Kubernetes.

Điểm giống:

```txt
Đều lấy Git làm nguồn sự thật
Đều sync manifest từ Git vào Kubernetes
Đều giúp giảm thao tác deploy thủ công
```

Điểm khác cơ bản:

```txt
ArgoCD có UI trực quan, dễ nhìn app Synced/OutOfSync/Healthy
Flux thiên về controller và CLI, phù hợp mô hình GitOps thuần YAML
```

Trong W9, em tập trung vào ArgoCD. Flux chỉ cần biết là một alternative.

Kết luận:

```txt
W9 dùng ArgoCD là chính.
Flux là công cụ cùng mục tiêu nhưng không phải trọng tâm lab này.
```

## 11. App of Apps là gì?

App of Apps là pattern trong ArgoCD dùng để quản lý nhiều Application con bằng một Application cha.

Khi hệ thống có nhiều app, ví dụ:

```txt
frontend
backend
database
monitoring
ingress
```

Nếu tạo từng app bằng tay trong ArgoCD thì khó quản lý. App of Apps giải quyết bằng cách tạo một app cha, trong app cha có các manifest Application con.

Mô hình:

```txt
parent-app
├── frontend-app
├── backend-app
├── database-app
├── monitoring-app
└── ingress-app
```

Ví dụ cấu trúc repo:

```txt
cloud/w9/day-a/argocd/
  root-app.yaml
  apps/
    frontend.yaml
    backend.yaml
    monitoring.yaml
```

Ví dụ child Application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: frontend
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/<your-user>/<your-repo>
    targetRevision: main
    path: cloud/w9/lab/frontend
  destination:
    server: https://kubernetes.default.svc
    namespace: frontend
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

Ưu điểm:

```txt
Dễ bootstrap nhiều app
Dễ quản lý toàn bộ platform từ một root app
Dễ review vì mọi Application đều nằm trong Git
```

Lưu ý:

```txt
App of Apps có quyền mạnh.
Chỉ nên cho người có quyền phù hợp sửa parent app.
Nếu sửa sai parent app có thể ảnh hưởng nhiều child app.
```

## 12. Sync Waves là gì?

Sync Waves dùng để điều khiển thứ tự apply resource trong ArgoCD.

Không phải tài nguyên nào cũng nên apply cùng lúc.

Ví dụ thứ tự hợp lý:

```txt
Namespace tạo trước
ConfigMap/Secret tạo sau Namespace
Deployment tạo sau ConfigMap/Secret
Service tạo sau Deployment
Smoke test chạy sau khi app deploy xong
```

ArgoCD dùng annotation này để đặt wave:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "5"
```

Số nhỏ chạy trước, số lớn chạy sau.

Ví dụ:

```txt
wave -1 = chạy trước tất cả
wave 0 = mặc định
wave 1 = chạy sau wave 0
```

Ví dụ Namespace chạy trước:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: demo
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
```

Ví dụ Deployment chạy sau:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
  annotations:
    argocd.argoproj.io/sync-wave: "0"
spec:
  replicas: 2
```

Ví dụ Job smoke test chạy sau deploy:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: smoke-test
  namespace: demo
  annotations:
    argocd.argoproj.io/sync-wave: "1"
spec:
  template:
    spec:
      containers:
        - name: test
          image: curlimages/curl
          command: ["curl", "http://web.demo.svc.cluster.local"]
      restartPolicy: Never
```

Kết luận:

```txt
Sync Waves = xếp thứ tự deploy resource.
```

## 13. Sync Phases / Hooks là gì?

Sync Phases là các giai đoạn trong quá trình sync của ArgoCD.

Các hook thường gặp:

```txt
PreSync = chạy trước khi sync chính
Sync = chạy trong quá trình sync
PostSync = chạy sau khi sync thành công
SyncFail = chạy khi sync thất bại
Skip = bỏ qua resource
PreDelete = chạy trước khi xóa application
PostDelete = chạy sau khi xóa application
```

Ví dụ dùng PreSync để chạy migration database trước khi deploy app:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/sync-wave: "-1"
spec:
  template:
    spec:
      containers:
        - name: migrate
          image: my-app:migrate
      restartPolicy: Never
```

Ý nghĩa:

```txt
Trước khi deploy app mới, chạy job migrate database.
Nếu job fail thì quá trình sync fail.
```

Ví dụ dùng PostSync để chạy smoke test:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: smoke-test
  annotations:
    argocd.argoproj.io/hook: PostSync
spec:
  template:
    spec:
      containers:
        - name: smoke-test
          image: curlimages/curl
          command: ["curl", "http://web.demo.svc.cluster.local"]
      restartPolicy: Never
```

Ý nghĩa:

```txt
Sau khi app deploy thành công, kiểm tra app có trả lời request không.
```

## 14. Rollback là gì?

Rollback là quay lại phiên bản trước khi bản mới bị lỗi.

Trong W9-D1 cần phân biệt 3 cách rollback:

```txt
git revert
kubectl rollout undo
argocd app rollback
```

---

### 14.1. Rollback bằng git revert

Đây là cách phù hợp nhất với GitOps.

Ví dụ lịch sử commit:

```txt
Commit A: image = web:v1
Commit B: image = web:v2
```

Nếu `web:v2` lỗi, em chạy:

```bash
git revert <commit-B>
git push origin main
```

Sau đó:

```txt
Git quay lại manifest cũ
ArgoCD phát hiện Git thay đổi
ArgoCD sync cluster về trạng thái cũ
```

Ưu điểm:

```txt
Git vẫn là nguồn sự thật
Có lịch sử rollback rõ ràng
Không tạo drift lâu dài giữa Git và cluster
```

Kết luận:

```txt
Trong GitOps, rollback nên ưu tiên bằng git revert.
```

---

### 14.2. Rollback bằng kubectl rollout undo

Lệnh:

```bash
kubectl rollout undo deployment/web
```

Lệnh này rollback trực tiếp Deployment trong cluster.

Ưu điểm:

```txt
Nhanh
Có thể dùng khi cần chữa cháy gấp
```

Nhược điểm trong GitOps:

```txt
Git vẫn ghi version lỗi
Cluster bị sửa tay về version cũ
Git và cluster bị lệch nhau
ArgoCD có thể sync lại theo Git và làm mất rollback
```

Kết luận:

```txt
kubectl rollout undo chỉ nên dùng khẩn cấp.
Sau đó phải sửa Git ngay bằng git revert.
```

---

### 14.3. Rollback bằng argocd app rollback

Lệnh:

```bash
argocd app rollback <APP_NAME>
```

Hoặc rollback về một history id cụ thể:

```bash
argocd app rollback <APP_NAME> <HISTORY_ID>
```

Cách này dùng lịch sử deploy của ArgoCD để quay về bản trước.

Tuy nhiên trong tư duy GitOps, nếu rollback bằng ArgoCD mà Git không đổi, thì vẫn có nguy cơ Git và cluster lệch nhau.

Kết luận:

```txt
argocd app rollback có thể dùng, nhưng cách sạch nhất vẫn là git revert.
```

## 15. So sánh rollback

| Cách rollback        | Tác động vào đâu         | Ưu điểm                         | Nhược điểm           | Khi nào dùng                      |
| -------------------- | ------------------------ | ------------------------------- | -------------------- | --------------------------------- |
| git revert           | Git                      | Đúng GitOps, có lịch sử rõ ràng | Cần commit/push      | Nên dùng mặc định                 |
| kubectl rollout undo | Cluster                  | Rất nhanh                       | Gây drift với Git    | Chữa cháy khẩn cấp                |
| argocd app rollback  | ArgoCD history / cluster | Dễ rollback theo history        | Git có thể không đổi | Khi cần rollback nhanh qua ArgoCD |

Kết luận cuối:

```txt
Ưu tiên git revert.
Nếu phải dùng kubectl rollout undo hoặc argocd rollback thì sau đó vẫn phải cập nhật Git.
```

## 18. Những gì em hiểu sau ngày D1

Sau ngày D1, em hiểu rằng GitOps không phải chỉ là dùng Git. GitOps là cách vận hành trong đó Git là nguồn sự thật của hệ thống.

Em hiểu rằng không nên deploy thủ công bằng `kubectl apply` trong quy trình GitOps, vì thao tác tay có thể làm cluster lệch khỏi Git. Thay vào đó, em cần sửa manifest trong Git, tạo Pull Request, để GitHub Actions kiểm tra, sau đó merge vào main và để ArgoCD sync vào Kubernetes.

Em cũng hiểu rằng ArgoCD giúp liên tục so sánh Git với cluster. Nếu trạng thái trong cluster khác với Git, ArgoCD có thể báo OutOfSync hoặc tự đưa cluster về trạng thái đúng nếu bật automated sync/selfHeal.

Về rollback, em hiểu rằng cách rollback sạch nhất trong GitOps là `git revert`, vì Git vẫn giữ vai trò nguồn sự thật. `kubectl rollout undo` có thể dùng khi khẩn cấp nhưng dễ tạo drift, nên sau đó vẫn phải cập nhật Git.

## 20. Tóm tắt ngắn để trình bày với mentor

W9-D1 em học GitOps và CI/CD. Em hiểu GitOps là mô hình lấy Git làm nguồn sự thật cho trạng thái mong muốn của hệ thống. Các manifest Kubernetes được lưu trong Git, GitHub Actions kiểm tra khi có Pull Request, và ArgoCD sync trạng thái từ Git vào Kubernetes sau khi merge.

Em nắm được 4 nguyên tắc GitOps: declarative, versioned and immutable, pulled automatically, continuously reconciled. Em cũng hiểu các khái niệm desired state, actual state, drift và reconciliation.

Về CI/CD, em hiểu GitHub Actions gồm workflow, event, job, step, action và runner. Với W9-D1, em dùng `pull_request` cho plan/check và `push` vào main cho apply-on-merge hoặc trigger GitOps flow.

Về ArgoCD, em hiểu Application là resource mô tả repo Git, path manifest, cluster đích và namespace đích. ArgoCD có thể báo Synced/OutOfSync và sync app vào cluster. Em cũng học App of Apps để quản lý nhiều Application con, Sync Waves để điều khiển thứ tự deploy, và các cách rollback trong GitOps.

Kết luận quan trọng nhất của em là: không nên apply manifest tay nữa; muốn thay đổi hệ thống thì sửa Git, tạo PR, merge vào main, để ArgoCD sync. Nếu lỗi thì ưu tiên rollback bằng `git revert`.
